# Markdown 文档的清晰度与信息密度

## 文档先回答一个问题

写 Markdown 前先确定读者读完要知道什么、决定什么或马上做什么。用一句话写出文件目的：

> 这份文档面向谁，解释什么，读完后要形成哪个判断或动作。

如果这句话写不出来，先收窄范围或重组材料，不要先增加背景、表格和说明。同一文档可以整合方案、依据与验证，但应围绕明确用途分层组织；是否拆分取决于读者、信息量和维护需要。

## 先给主线，再给材料

解释一个研究判断时，可按以下顺序组织：

1. **结论或当前判断**：现在是什么情况；
2. **关键理由**：为什么得到这个判断；
3. **证据或实现**：哪些数据、代码、来源或运行支持它；
4. **影响和动作**：这意味着什么，下一步做什么。

方法推导、接口说明和正式论文按各自的逻辑与格式要求组织。读者只看标题、开头段和每节第一句，也应能复述文档主线；细节用于支撑主线。

不要用“背景—意义—相关工作—方法—结果—讨论”的空模板替代实际逻辑。每一节都要回答一个具体问题，例如：

- 当前真正卡在哪里？
- 哪个实验区分了哪些解释？
- 这次改动改变了什么行为？
- 结果支持哪项主张，又不支持哪项主张？
- 用户现在应该采取什么动作？

## 一段围绕一个主要判断

每个段落围绕一个主要判断展开，可以在其中连接理由、证据与推论。段落之间应有真实的因果、转折或递进关系，不使用连接词堆出表面连贯。

段落写完后检查：删掉这一段，后面的判断是否失去必要台阶？如果没有，这段可能是在重复、铺垫过度或展示工作量。把多个段落都能归纳成同一句话时，合并它们，并保留能改变结论的细节。

事实、解释、计划与局限可以共同支撑一个判断，但读者应能分清它们。尤其不能把预期结果或待运行实验写成已完成事实；操作细节和背景只保留当前读者需要的部分。

## 解释逻辑，不堆完整性

严密不是把所有可能的质疑、边界和免责声明都写进正文。真正需要保留的是会改变推理的条件；其他内容放到合适的限制、附录、实验记录或验证清单。

解释研究结果或方法判断时，按需要交代：

1. 观察到什么；
2. 它与哪个比较或机制有关；
3. 因此支持什么判断；
4. 还不能推出什么。

适用边界只在影响理解或容易误读时展开，不能把每段都改成自我辩护。没有足够证据时直接写“目前无法判断”，并给出解除未知所需的最小动作；不要用一串“可能、一定程度上、在一定条件下、仍有待进一步”掩盖没有结论。

## 标题和表格要承担判断

技术方案和研究记录的标题应让读者预期具体内容，例如“现有方法为何在观测缺失时失效”“收益来自模型结构还是训练预算”。结论尚未成立时使用问题或真实状态；正式论文和规定格式的材料遵循其章节要求。

表格不是段落的收纳箱。每一行至少要有一个明确含义：比较、状态、缺口、动作或决策。列名和行顺序应帮助读者得出结论；如果表格只是在搬运大量数字，先写一句读者应从表格看出的结论，并删去不影响判断的列。

## 清晰度复核

交付前先不看正文细节，只看标题、目录、每节第一句和最后一句，回答：

- 这篇文档到底要说明什么？
- 哪个判断最重要？
- 判断是怎样一步步得到的？
- 哪些内容只是证据，哪些内容是结论？
- 读者应形成什么认识或作出什么决定？

如果无法回答，先重排标题和段落，再做语言润色。不得用增加背景、补充免责声明或扩大表格来掩盖主线不清。
